# 端到端加密故障隔离、恢复与旧版兼容优化计划

日期：2026-09-07。状态：**方案已制定，待实施；本轮不修改应用代码、测试、配置或用户数据。**

规划基线：`codex/pro-purchase-foundation`，本轮启动 HEAD `ab3a60ac1`，基础 `main@8edc18786`。同分支有并行 Pro/SSH/远程 AI 工作，实施前必须重读共享状态并核对相关源码差量；本文不接管原活动任务，不声明任何修复已交付。

## 1. 目标与范围

本计划只面向“设置 → 数据安全 → 端到端加密”开关及实际依赖该开关的功能。优先目标是：**故障影响停留在最小必要的数据、操作和模块内；健康数据和不依赖故障数据的功能继续可用，同时保留恢复机会。** 其他已确认的问题仍逐项修复，不以故障降级替代根因修复。

产品与实施边界：

1. 从未开启加密，或用户成功主动关闭后，按原产品选择保存和同步，不将明文本身列为缺陷，不强制加密。
2. 已开启但已锁定，仍是已经选择加密。读取失败、缺少内存密钥或后台恢复失败，不能被当成“未开启”而写入/上传明文。
3. 覆盖主密码、DEK、受保护字段、云同步、加密备份恢复、账号转换，以及直接复用 DataCrypto 的 SSH 命令/收藏与会话日志。
4. 纳入老版本已开启加密及相关功能的数据：覆盖保留数据升级、旧云数据拉取、旧加密备份、旧附属存储、迁移中断和仍有旧端写入的场景。
5. RustDesk 等远程协议传输加密、普通文件全盘加密、全部元数据加密、系统备份开关和通用清理问题，不作为本开关的修复任务。旧备份兼容等通用路径，只纳入加密数据正常承接所依赖的部分。
6. 数据可用性不意味着绕过认证：无法确认账号归属、密钥、AAD 或目标信任时，只限制必须依赖这些条件的操作，提供明确恢复路径；不返回伪造数据、不清空坏记录、不自动改用明文。
7. 不承诺丢失密钥或密码学认证失败的数据必然可恢复。应保证“原始数据保留、影响可见、好数据可用、后续恢复有入口”。

本计划不继续采用前一份广义报告的“24 项/9 项高优先级”口径。下文 F 编号仅用于追溯已讨论的具体问题。

## 3. 不可破坏的验收原则

| 编号 | 原则 | 可观察判据 |
|---|---|---|
| I01 | 局部损坏不升级为全 App 不可用 | 一条坏密码不使正常主机消失，不使其他密钥/TOTP/设置不可用 |
| I02 | 附属功能故障不阻断主流程 | 日志存储失败时 SSH 连接、输入和 SFTP 继续工作；停止故障日志写入并提示状态 |
| I03 | 好记录不依赖坏记录才能解锁 | 主密码验证成功后，已认证的健康记录可用；迁移/坏行状态单独展示 |
| I04 | 原始密文与关联关系保留 | 认证失败不变成空密码、删除、墓碑或空列表；重开后仍有恢复入口 |
| I05 | 已开启时不发生隐式降级 | 故障注入前后受保护字段不以明文新写入主库、旁路库、队列、诊断或云端 |
| I06 | 不因升级自动换钥 | 缺省旧 KDF 按经确认的旧算法解释；不生成新盐覆盖旧配置、不要求重新开启开关 |
| I07 | 迁移幂等且可恢复 | 任一持久化边界终止进程，重开后可确定旧态/新态/待恢复态，重试不重复/不丢记录 |
| I08 | 恢复不混钥、不悄悄丢项 | 合并后每个保留敏感字段有明确密钥归属；坏项保留且不覆盖目标健康值 |
| I09 | 云故障不阻断可信本地使用 | 账号与本地 DEK 已验证时，云不可用只暂停同步；本地加密提交和持久脏标记共同成功 |
| I10 | 账号和信任边界保持严格 | 不能为了继续使用而借用另一账号数据、旧 lease、旧目标信任或未经确认的新主机 |
| I11 | 故障提示可操作且不刷屏 | 告知影响的具体功能/数量、可用部分、重试/修复入口；不把所有错误都提示密码错误 |
| I12 | 恢复路径不依赖唯一坏模块 | 主列表能显示受影响条目与恢复入口；日志/收藏自身打不开时仍能从数据安全页进入修复 |

## 4. 故障状态与操作准入设计

### 4.1 分离四种事实

在现有 API 上逐步引入明确结果，不一次重写所有调用方。拟定类型名只表示职责，实施时遵循 ArkTS 与项目命名习惯：

- **配置事实**：`unconfigured / configured / unavailable`。只有有证据的未配置才允许走合法未加密模式；存储错误不能返回 unconfigured。
- **密钥事实**：未解锁、已验证、参数已变化、参数不受支持。DEK 与已验证的参数指纹和账号 lease 绑定。
- **数据健康事实**：按存储/记录/字段记录 healthy、待迁移、旧钥、损坏、不支持、存储不可用。不能用一个布尔 ready 代表整库健康。
- **操作结果**：成功、部分成功、未提交、已提交但后处理失败、可重试、需要解锁/源密码/用户选择。结果携带无秘密的错误码、影响范围和下一步。

`DataCrypto` 的“密钥验证成功”不再等待所有记录迁移成功才可成立；但业务写入仍须逐次验证 owner、storeInstanceId、generation、参数指纹及所操作记录的健康状态。全局阻塞只用于该操作确实无法满足的前置条件，不用于单条字段认证失败。

跨存储转换时，另有持久化的提交决定与参与者进度，优先于仅凭 cryptoparams 推断整个 App 已完成转换。特别是“关闭已提交、部分存储待完成”必须是一种可恢复的明确状态，不能冒充全部关闭成功，也不能继续显示所有数据均处于已开启保护状态。

### 4.2 各类故障的目标行为

| 故障 | 继续可用 | 最小暂停范围与恢复路径 |
|---|---|---|
| 单主机保存的密码损坏 | 主机基本信息、其他主机、普通设置；已有授权会话按原策略运行 | 暂停使用该密码；可重新输入仅用于本次连接，或明确替换坏密码 |
| 共享 SSH 私钥损坏 | 不依赖此 key 的主机、其他 key、现有 SSH 会话 | 显示依赖此 key 的主机；允许已有连接策略支持的其他认证方式，不自动切换认证/信任 |
| 一个 TOTP 种子损坏 | 其他 TOTP 条目正常计时与复制 | 该条显示不可生成及恢复入口，不生成假码、不整页报错 |
| SSH 收藏/命令库不可用 | 终端、SFTP、手工输入命令 | 收藏面板显示局部异常；不把空文档写回去覆盖原库 |
| SSH 日志索引或一个块不可读 | SSH 连接/输入/SFTP；可读日志块与元数据 | 暂停受影响日志持久化，不自动删坏块；给出重试/导出原密文/重建索引入口 |
| 云超时、注册失败或单个可选表异常 | 可信本地加密数据读写、健康协议模块 | 暂停对应同步域；有界重试，不空库上传、不影响账号本地可用性 |
| 受保护参数缺失、被替换或不受支持 | 公共设置、可验证的元数据、不依赖密钥的功能 | 暂停需该钥的读写/上传；重拉同账号可信参数或让用户解锁，绝不自动重新配置 |
| 主 RDB 物理不可用/磁盘满 | 已建立且不依赖新增持久化的会话、帮助/诊断；可行时提供不保存的临时连接 | 依赖持久化的操作真实失败；只使用现有已验证的同账号回退库策略，不生成空库假装恢复 |
| 账号切换无法安全结束旧操作 | 原账号中仍安全的界面和明确取消/重试 | 保持转换未完成，不让新账号接收旧结果；不得绕过原 SensitiveDataBarrier |

临时认证凭据只存在于对应连接的内存和一次性交接中，不自动保存、不进入日志/命令历史，结束后清理。主机/网关/代理信任仍需现有校验；当信任数据不可用时，必须显式重新核验，不能默认信任。

### 4.3 避免“部分可用”产生静默数据损失

1. 查询返回健康记录加受影响条目的可见占位，附健康摘要；不能 catch 后静默跳过整行。
2. 缺少密码、认证失败、用户明确清除、未知版本分别表示。继续复用 keep/replace/clear；名称或排序编辑不应重写未经认证的秘密。
3. 坏字段仍保存原字节、原 owner/表/记录/字段上下文和参数指纹。旁路隔离信息为本地数据，不新增 AGC 云列。
4. 编辑健康字段不能上传一个省略坏秘密的整行，造成云端清空。**本地逐行可用与云同步粒度分开处理**：当前 CloudStore 使用 `cloudSync(mode, [table], ...)`，安全回退是暂停最小物理表及必要密钥依赖域的同步，保留其中健康行的本地加密读写与持久脏意图；其他可独立验证的表继续同步，不承诺坏行所在同一表的健康行仍能单独上传。
5. 只有已验证属于当前账号/密钥代次的健康数据可以同步。坏密文/未知版本保留为不透明原始数据，但不因“长得像密文”就当成可上传的新值。
6. 隔离空间不足时不删原始记录腾空间，也不谎报隔离成功；限制相应写入并说明磁盘问题。临时失败不得触发后台自动清库。

API 26 的 `cloudSyncEx`/谓词能力只作为 E0 的可行性核验：必须先验证真实 AGC 的上传、下载、删除、脏标记与冲突语义，并保留 API 23 的表级回退。未验证前不依赖它放宽准入。不能通过从分布式表删除坏行来“隔离”再同步，以免上传墓碑；沿用应用显式协调、autoSync=false 的边界，先排空已有同步再变更同步资格。

### 4.4 可用性与重试的测量标准

以下是待 E0 基准校准的验收目标，不是已测结果：故障模块不能成为主列表和正常会话的启动必经等待；耗时操作开始后 300 ms 内显示状态/可取消入口；分批迁移运行时受控交互的 P95 响应目标不超过 100 ms，按设备与数据规模记录。单批同步 CPU 工作预算先以 8 ms 控制，再以实测调整批量，不把整个数据集塞进主线程一次处理。

每类 I/O/KDF/云操作必须有明确的截止、并发数和重试预算；超过预算返回局部可操作状态。超时仅表示调用方不再等待，底层未停止的操作仍需 generation/CAS 防止迟到提交。不同模块独立重试，同一 owner/operation 只能一个恢复任务执行；用户取消后不在后台自动重新发起破坏性转换。

## 5. 密钥一致性与故障封堵

### 5.1 参数指纹与写入租约

规范化解析盐、verifier、KDF 算法/版本/迭代、key version、verifier version、envelope 规则及作用域/epoch；同一合法配置的缺省字段按对应历史版本唯一解释。对有效规范表示计算参数指纹，避免只比较 active 字符串。

- 指纹变化：立即使旧 DEK 和其派生缓存失效，取消在途敏感写入；局部 UI 可用性按第 4 节处理。
- 提交前再核验捕获的 lease、storeInstanceId、generation 和指纹；旧任务不能在新配置下提交。
- 参数与记录不同步到达时，先保留原始同步结果和上次可信状态，不用新参数盲试旧记录，也不把解密失败转为删除。
- 首轮方案保留现有 DEK 派生方式，**不自动改盐、迭代、密钥结构或全设备 epoch**。KDF 升级/改密事务待迁移与兼容机制通过后再执行。
- 本地指纹是失效与一致性工具，不是云端参数真实性证明；远端 reset/disable 继续遵守现有已验证生命周期限制，不因状态值改变自动清空或解密落盘。

### 5.2 优先封堵已知破坏性入口

在大规模迁移前先完成：异钥备份禁止直接合并；日志认证失败禁止按孤儿块自动删除；单行解密失败不隐藏主机；错误参数禁止进入无界同步 KDF；没有可靠配置状态时禁止重新 setup 覆盖旧参数。

这批改动应能独立验收，不等待新密文格式、恢复密钥或整个数据层重构。

## 6. 统一迁移参与者与恢复事务

### 6.1 明确登记范围

建立内部参与者清单，至少包含核心敏感表/本地扩展、VNC 的既有受保护 secret 模式、SSH Productivity Preferences、SSH 会话日志索引与块。按实际实现核对 RustDesk 账号 JSON 等嵌套敏感字段。独立 Asset 身份、外部私钥原文件和普通下载文件不被顺手转换。

每个参与者提供：作用域/存储定位、格式能力、只读清点、健康分类、prepare/验证/提交/恢复、清理回执、锁定与 generation 失效。初始化失败返回局部状态，不能阻止不依赖它的参与者服务。

### 6.2 跨 RDB/Preferences 不假设原子事务

主 RDB 内继续使用真实事务；RDB、Preferences、日志库之间采用持久协调日志、可验证暂存和幂等恢复，不能用 Promise.all 包装后声称跨库 ACID。

| 阶段 | 必须持久化/验证 | 失败或重启后的行为 |
|---|---|---|
| inventory | operationId、来源 owner/store、源参数指纹、参与者、原记录计数及修订 | 无法确认来源则停止该转换，旧数据保持权威 |
| prepare | 各参与者的候选数据、源/目标格式、校验摘要、进度；原数据仍保留 | 失败只重试失败参与者，健康旧态仍可读；暂存不能包含额外明文秘密或明文 DEK |
| validate | 目标候选可认证、数量和引用一致、坏项单列且可恢复 | 未通过者不发布；不能以“跳过坏项”冒充完整迁移 |
| publish | 短时约束受影响写入，逐参与者发布并记录回执；主库参数/业务提交遵循真实事务 | 使用日志确定已发布部分与仍应读取的源版本；不把半次发布当 disabled/empty |
| reconcile | 重开后按回执验证权威数据，重放安全未完成步骤 | 必要时要求原密码重新解锁；不会因进程重启而依赖已丢失的内存 DEK |
| finalize | 全部必须参与者验证完毕，再结束转换、清旧引用/参数和暂存 | 失败保留恢复材料，已可用模块不因可重试清理失败全部失效 |

**源数据并发约束：** inventory 记录本地单调源修订和记录/槽位摘要，不能只相信可被时钟影响的 updatedAt。prepare 期间原写入继续在已验证源代次中进行，并原子登记增量脏日志；新增、修改、删除、日志追加均须覆盖。发布前重放增量、重新验证候选，并以源修订比较更新（CAS）确认没有遗漏新变化。

RDB 数据与增量日志同事务提交；Preferences/日志通过统一参与者写入口及持久序号协调，跨窗口/进程不能只靠各自的 JS 单例互斥。无法提供可靠修订/CAS 的参与者先使用其局部短写入栅栏，不能声称它支持并发无损迁移。栅栏内不等待网络/KDF/用户交互；高频日志可暂停记录以取得稳定发布点，但不暂停 SSH 主会话。

CAS 冲突时废弃对应过时候选并按最新源修订重新准备，不覆盖较新记录、不复活已删除项。自动重试设定有界次数，持续修改时暂停此参与者的迁移并允许稍后继续。崩溃重开后重新核验源修订和增量水位，不直接重放一个失效的旧候选。

**关闭加密的唯一提交点：** 上表的 publish 必须遵循以下顺序，不能任意挑选参与者先转明文：

1. 全局提交决定前，旧加密配置/源版本仍权威。所有候选、恢复材料和暂存秘密保持加密；此时失败或取消可以丢弃未发布候选，继续已开启的源状态。
2. 每个参与者完成 prepare/validate/CAS 并冻结对应发布版本后，在主 RDB 的单个事务中持久化唯一 `commit_decision`。记录绑定 operationId、owner/store、源与目标参数指纹、参与者名单、目标位置、修订水位及用户明确接受的排除项；该记录不能仅存在内存或散落于多个 Preferences。
3. 决定持久成功后，才允许依用户已确认的关闭选择物化目标明文。状态为“关闭已提交，转换中”；以后仅幂等前滚到目标，不再把失败描述为“已回到完全加密”。主库与旁路读写根据每个参与者回执选择已验证的源/目标代次，而非只查主库盐是否为空。
4. 未完成参与者的源密文、参数和恢复入口保持；重启后必要时让用户用原密码继续完成，不自动新建空库。已完成参与者继续可用；待完成模块准确提示自身影响，不能因此锁住所有健康模块。
5. 全部必需回执及源修订验证完成，再结束关闭并清理旧引用/参数；清理失败记录为可重试后处理。云同步栅栏覆盖完整转换期，关闭后按既有策略暂停敏感云同步，不把临时明文或半次转换上传。

**提交后的写入与恢复约束：** 从最后一次 CAS 到该参与者的目标数据与激活标记原子持久化前，持续保持这个参与者的发布写栅栏；未激活参与者不能接受会改变冻结源水位的持久化写入，但可验证的源数据读取和无依赖主流程仍可用。激活后仅按目标代次写入，其他已经激活的参与者不等待失败参与者。发布栅栏只覆盖原子切换所需步骤，不能拿着它等待网络、密码输入或全量 KDF；失败时给出局部状态和重试入口。

参与者恢复先读取本地持久化的 operationId、目标代次和激活标记；即使全局回执尚未补齐，也只能验证并补写回执，不能把旧候选再次覆盖已经激活且发生新修改的目标。主 RDB/日志的目标数据与激活标记同事务；Preferences 采用单槽封装或其他经真实平台验证的原子发布方式，未证明前不以多个 put/flush 冒充原子切换。全局清理必须等这些标记与回执一致。

如果主 RDB 连提交决定都无法可靠保存，此次关闭未提交，仍以源加密状态为准。若之后需要撤回一个已经提交的关闭，必须设计并验证独立补偿转换，不能把简单 flag 翻转当回滚。启用/重置也须明确自身提交点、明文可见性及提交前后可取消边界；未知中断状态不得直接从 cryptoparams 推断为无数据或未配置。

实施前须以最小原型证明主库与两种旁路持久化的提交/重启选择规则。不能为了实现暂存更改现有 canonical 云物理库名、绕过平台身份或把新协调字段上传既有云表。

协调日志不保存主密码或明文 DEK。保留的旧参数只用于重新派生正确源钥，不能随意替换当前参数；原密文与必要上下文可留作恢复。日志/暂存中的秘密内容保持加密且仅在本机；清理失败有有界重试和可见状态。

### 6.3 启用、关闭、重置的具体规则

- **启用**：先清点已有受保护数据；配置建立和主表转换保持事务一致。后续允许分批完成可重试迁移，但 UI 必须区分“保护已配置”“旧数据迁移中”“存在待处理项”；不得对尚未转换的目标数据宣称全部已加密。已有模糊前缀数据按第 7 节来源规则处理。
- **关闭**：不先删盐/verifier/旧参数再处理旁路数据。提交决定前失败保持源加密状态；提交决定后失败按第 6.2 节前滚，显示已提交但尚未完成。全部依赖该钥的已确认数据必须完成转换与验证，或者用户明确选择保留经验证可恢复的加密包并了解该模块暂不可读，才能宣称关闭完成。不得将未完成流程默认重置成 disabled 或 empty。
- **重置**：预览准确清理范围、坏项数量与不可恢复影响；默认提供保存原始加密恢复材料的路径。重置明确确认后才清理选定数据，不把解锁失败/自动迁移失败导向自动重置。
- **重新启用**：按新配置处理新数据，不能把仍属旧钥的数据标记成新钥已迁移；旧密文通过保留参数/用户提供旧密码单独恢复，不能解开则保留并明示。
- **锁定**：清理 DEK、主密码草稿、相关解密缓存和旧 generation 文档；SSH 日志只返回无秘密的健康状态，不能继续暴露已解密 snapshot。既有远程会话保活按原策略，不属于强制全部断开的需求。

## 7. 老版本数据正常承接与兼容

### 7.1 先建立“版本 → 实际写入能力”清单

升级承接以真实历史实现生成的去敏固定样本为准。现有 `verify_legacy_upgrade.py` 包含 1.0.7、1.0.8-initial、1.1.1-initial 的不可变源码基线，分别为 `d2bc6c9982`、`a3d47c464a`、`62c171778c`；这些标签证明 schema 来源，不证明各版本均已支持同样的 E2EE/SSH 日志功能。

E0 必须从本地受控历史源码确认：每个版本何时出现开关、KDF/verifier 规则、字段格式、VNC 子版本、主机历史 `passward`/扩展字段映射、命令/日志保存方式、备份格式。补上首次支持每种相关功能的版本和修复前最近稳定版本。记录源码 hash、生成方法、样本 hash 和预期明文摘要；不能把当前编码器生成的样本冒充旧 App 数据。

历史私有 refs/归档仅本地读取，真实秘密不得进入仓库、日志、测试包或云端；测试样本使用虚构密码、key 和 TOTP 种子。历史构建不可用时，基于不可变旧写入实现生成样本并明确标记，真实旧 HAP 保留数据升级仍是单独验收项。

### 7.2 兼容策略

| 来源数据 | 读入和升级策略 | 必须保留的边界 |
|---|---|---|
| 旧 app 已开启，缺少新 KDF/verifier 元数据 | 只有匹配已知历史形状时，采用该版确定的缺省值验证原主密码 | 缺字段不能自动生成新盐；畸形显式参数不能悄悄套缺省值 |
| 旧 v1 核心字段 | 保留旧解密器，认证成功后按计划迁移；迁移前原字节保留 | 不要求用户重输每台主机密码；不把所有 v1 立即禁止 |
| VNC v2 / 现有 v3 | 分别遵循真实版本的 AAD、secret kind、key version、epoch | 不用普通 v1 迁移器硬读 VNC v2，不改 owner/id 后再尝试原 AAD |
| 新旧格式混合、迁移中断 | 逐记录判定格式与参数归属，恢复进度幂等重放 | 一条未迁移不阻止好记录；不能覆盖原始未知/损坏密文 |
| 已开启用户的旧明文残留 | 仅在旧存储形状和来源可证明时当明文迁移，阻止未加密上传 | 显式用户输入与历史存储分开；`2026:...` 不可单靠前缀判为密文或自动放行 |
| 旧账号 raw owner、空 owner、旧物理库 | 复用平台身份/owner 归属证明与历史恢复回执；先保存完整来源视图 | 不把全部空 owner 行自动归给当前账号；不让 AAD 绑定被直接改坏 |
| SSH 旧明文命令、v1 密文槽位 | 保留按 owner 的原槽位，验证旧格式后迁移到可追踪版本 | 原子槽位写入失败保留旧值；不返回空集合后持久化覆盖 |
| SSH 旧全局日志 root/块 | 先证明所属账号和可验证源钥，再迁移为 owner/密钥代次隔离 | 归属不明先隔离，不能由第一个登录账号领取；无法解密不能执行孤儿清理 |
| 已开启用户的 v1/v2/v3 备份 | 正确按文件版本校验，再按第 8 节处理密钥与上下文 | 旧摘要按原格式核验，规范化在其后；缺少可选 section 不清空目标数据 |
| 未来/不支持格式 | 保留原始包/行，标为需更新或待恢复，其他健康记录可用 | 不按明文解读、不自动降版本、不擦掉未来字段 |

旧主密码必须按原字节/编码语义验证，不 trim、不自动改大小写或 Unicode 规范化；新密码规则只用于新设置/用户明确改密，不能阻止老用户用原密码解锁。短旧密码可提示后续升级，不强迫在恢复数据前改密。

### 7.3 保留数据升级与长期共存分开验收

**主要承诺：旧 App 已开启后的数据，升级到修复版时能正常承接，不卸载、不清库、不重新 setup。** 解锁后显示真实记录/可恢复条目计数，所有可认证的旧数据均应可使用；原有账号、分组、引用和同步选择保持。

多设备仍有旧客户端时，还需验证它如何读取新数据、保存旧格式、覆盖参数/行以及处理未知字段。仅新客户端“能读旧数据”不代表新旧端可任意双向写。

- 首轮不自动升级既有用户的盐、KDF 工作因子、DEK 结构或云字段格式，优先在现有协议内修复恢复和失效逻辑。
- 新写入/迁移目标格式必须来自实际共存矩阵，不擅自新增 v4、双写明文或将已认证密文降级为兼容低版本。
- 对无法证明安全共存的变更，暂停对应云格式升级/破坏性迁移，保留可验证的本地使用和原始云数据；明确所需客户端升级条件。
- 旧端更新了某条合法旧格式记录时，新端应逐项导入并保留冲突，不能因一条旧格式重新把账号整体锁进恢复状态。
- 旧端是否支持新格式/高版本 schema 必须实际验证。数据迁移后的 App 降级不是默认回滚方式，不能拿旧 binary 打开未知新库。

## 8. 加密备份、恢复与坏数据修复

### 8.1 恢复前先做只读预检

检查文件版本、大小、原始摘要、来源 owner、完整参数集合、已知格式/尺寸、记录数、重复 id、依赖、所需源密码与目标密码。加密参数必须成套有效；manifest 声称已加密不能只靠 cryptoparams 非空。

预览区分可直接恢复、需源密码、与当前记录冲突、损坏/未知、被规则排除的本机数据。用户确认的是这份具体结果；变更文件、账号、数据库实例或参数指纹后重新预检。

### 8.2 目标状态与源数据的处理

| 目标状态/来源 | 处理方式 |
|---|---|
| 已开启且已解锁，备份与目标同钥/同上下文 | 按 ID 与修订合并，验证字段，保护目标健康新记录和缺失 section |
| 已开启且已解锁，备份为另一套密钥 | 先分别验证源/目标密码，逐条解密源并用目标 AAD/DEK 重加密；不覆盖目标 cryptoparams |
| 已开启但已锁定 | 可以只读预览；敏感提交前解锁目标，不能先把原数据落成明文 |
| 已开启，导入可信旧明文备份 | 在受控内存/加密暂存中规范化，按目标钥加密后再激活/同步；来源明文文件由用户管理，不额外散落副本 |
| 未开启，导入加密备份 | 明确让用户选择恢复原加密配置或解锁源后按未加密模式导入；不得静默启用、关闭或生成另一把钥匙 |
| 源密码缺失或部分坏行 | 不覆盖当前健康数据；保存原密文和恢复材料，可按确认导入可验证的好记录，报告待恢复项 |
| 来源账号不匹配/归属不明 | 保持现有跨 owner 限制；不能只改 owner/id 绕过 AAD 与账号准入 |

“部分恢复成功”必须有逐项结果和原始保留位置；不能把备份中没有的记录当成用户要求删除。恢复后的云放行仍经现有 bootstrap/quarantine 规则，验证源数据没有把旧参数或空表反向覆盖新状态。

### 8.3 用户可操作的恢复中心

数据安全页提供受影响模块与记录数量、最后失败原因、重试、验证旧密码、恢复加密备份、重新输入/替换单条秘密、导出原密文恢复材料；原始敏感内容默认不回显。操作必须能在坏模块无法初始化时进入。

用户选择替换一条坏秘密时，明确只替换该字段；先验证新输入可用或明确告知尚未连接验证，再原子保存。原密文保留至恢复操作完成或用户明确删除。清理期限与最大空间有独立策略，不用每日自动清理掩盖认证失败。

整包备份认证可另行设计作为增强项；首轮必须解决加密字段的可恢复性和异钥混合，不能以“整个 JSON 没有再加一层密码”认定现有密文字段已经泄漏。

## 9. KDF、输入规则、体验与诊断

1. KDF 接收严格的受支持算法/版本/编码/尺寸及有界整数参数；已知历史缺省值和畸形输入分开。最大值及合理超时在 E0/E1 通过目标设备基准和旧样本确认，不拍脑袋拒绝合法老用户。
2. 派生使用本地 SDK 已核验的异步或工作线程方案；调用取消/账号切换后结果丢弃，单个操作有并发限制。不能只套 async 函数却仍在 UI 线程运行同步 KDF，也不能靠超时 Promise 假装同步任务已停止。
3. 解锁结果区分错误密码、限流、参数缺失/不支持、密钥已变化、平台失败、存储失败、部分数据受损；只有密码验证失败才计密码错误，不用存储故障增加错误次数。
4. 主密码验证、保护配置、数据健康与迁移进度分开展示。取消/关闭弹层/后台/失败终态清理输入草稿，不重复执行已成功提交的全量迁移。
5. 故障发生时优先单次局部提示，后续在模块入口显示状态；对同一故障合并重试，采用有界退避和单次执行，避免首屏等待所有旁路模块完成或循环弹窗。
6. 诊断只记录固定错误码、模块、版本、状态、数量、耗时桶和随机 operationId；不输出密码、DEK、私钥、TOTP、终端正文、密文全文或可跨设备长期关联的账号标识。原密文恢复包与普通诊断导出分开，用户显式选择。
7. 给出本地健康摘要：总条目/可用/待解锁/待迁移/待恢复/同步暂停，并解释计数口径；不把未加载和零条数据混同。

## 12. 发布、回滚与完成标准

1. 首先发布可独立验证的故障封堵与局部可用修复，不自动推动不可逆格式/KDF升级。诊断、只读健康扫描先于数据重写启用。
2. 迁移按功能/数据批次可暂停；重启从协调日志恢复，不重跑已经完成的整库转换。暂停不丢密钥参数，不破坏已发布健康数据。
3. 以测试/受控用户验证“无丢项、无意外明文、坏项局部隔离、原密码可继续使用”为扩大范围的前提；没有线上指标系统时不假称已经拥有灰度基础设施。
4. 回滚优先停止迁移并使用保留且经验证的源数据/兼容读取路径。已经提高 schema 或写入旧版不理解的数据时，禁止未经测试降级 App；回滚工具与源码发布同样验收。
5. 兼容样本、故障矩阵、设备/云证据和独立审查逐阶段记录。出现无法恢复/新混钥/明文降级即暂停相关迁移/发布，不用删除用户数据恢复“绿色状态”。
6. 最终完成要求：范围内发现逐项闭环；T01–T24 的适用项有证据；历史升级/双设备关键项没有以“待测”冒充通过；坏数据保留、健康功能可用、用户恢复入口可达；无未解决的交付阻塞审查项。
