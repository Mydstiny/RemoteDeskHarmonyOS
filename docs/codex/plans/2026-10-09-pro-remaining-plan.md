## 1. H 主机健康中心（第一优先）

### 1.1 现状

- `HostListPage.ets` 已按协议做在线探测：
  - RDP：证书探测，含 RD 网关证书；
  - VNC：证书探测；
  - SSH：主机指纹探测，走主机配置的代理或跳板；
  - RustDesk：对端是否在线；
  - Moonlight：`MoonlightLanProbeService` 局域网发现。
- 结果只写进 `RemoteHost.lastHealth`（五档）和 `lastLatency`，卡片上显示「连接正常 · 2 ms」。VNC 的结果只留在页面内存里。
- 失败一律显示「未检测到主机」，不区分原因。没有历史记录，也没有统一入口。
- 原生探测其实已经分阶段执行。例如 RDP 证书探测的日志有 resolve、tcp、negotiation、tls 各阶段，还有 rootTrusted、hostMismatch。但这些信息没有返回给 ArkTS。
- 高级主机管理已有多选批量连通检测。

### 1.2 首发范围

**原因分类**：把「为什么不可用」分成 8 类，用白话显示：

| 状态 | 白话 | 能从哪里得到 |
|---|---|---|
| reachable | 可以连接 | 各协议探测成功 |
| route_unavailable | 找不到主机或网络不通 | DNS 失败、TCP 拒绝 |
| timeout | 超时 | 任一阶段超时 |
| trust_required | 证书或主机指纹需要确认 | RDP/VNC 证书不受信或主机名不匹配；SSH 指纹与已保存的不一致 |
| remote_rejected | 远端拒绝了连接 | 协议协商被拒（例如 RDP 只允许某种安全层） |
| peer_offline | 对端不在线 | RustDesk ID 服务器报告离线；Moonlight 发现不到 |
| capability_unsupported | 这台主机不支持这种检测 | 例如 RustDesk 直连模式 |
| unknown | 无法判断 | 其他情况，附固定错误码 |

认证失败（密码错误）首发不做：主动检测不使用凭据，也就无法判断。只有用户真正连接失败时，才把连接结果记成一条观察。

**历史**：每台主机保留最近 20 条观察（时间、状态、延迟、路径、错误码）。只存本机，不云同步。删除主机或切换账号时清理。

**界面**：
- 卡片：健康点旁边显示「3 分钟前」。超过 1 小时的结果变灰，并标「待刷新」。
- 主机详情新增「健康」页，包含：
  - 当前状态和白话原因；
  - 路径：直连、网关、中继或代理，以及实际用的是 IPv4 还是 IPv6；
  - 最近 20 次的延迟小图；
  - 一个建议操作，例如「去确认证书」「查看指纹变化」「检查中继」。
- 批量检测面板：可以检测选中的主机或全部主机，显示进度，结果按原因分组。

**AI**：诊断助手可以读取所选主机的观察摘要（已脱敏），回答「为什么连不上」。它不能直接修改证书信任或安全设置，只能给出跳转按钮。

**免费与 Pro 的划分**：免费保留现有的单点在线检测和卡片显示。Pro 包括原因分类、历史、详情页、批量面板和 AI 解读。

| 阶段 | 内容 | 主要文件 | 完成条件 |

| H0 | 状态、错误码白名单、各协议探测结果到状态的映射、过期判断 | 新增 `services/pro/health/HostHealthPolicy.ets` 和 node 测试 | 映射表每一行都有测试；未知输入只能落到 unknown |

## 2. E 会话截图与证据包（第二优先）

### 2.1 现状

- RustDesk 顶栏「显示」菜单里有「截屏」，但它是灰着的占位，说明文字是「截屏需要本地截图保存和权限链路接入后启用」（`RemoteSessionTopBarPolicy.ets`）。
- 渲染器 `GLRenderer` 没有读回像素的能力。RDP、RustDesk、VNC、Moonlight 用的都是这同一个渲染器：硬解走 `PresentFrame`，软解和 RDP 走 `PresentRawBGRA`。在这里做一次，四个协议都能用。
- 诊断抓取（`DiagnosticCaptureRuntime`）、视频诊断证据（`VideoDiagnosticEvidence`）和反馈邮件（`AiMailService`）都已经有了。

### 2.2 首发范围

- **截屏**：只截远端画面，不包括本地工具栏，按远端原始分辨率截取。截完先预览，然后可以：
  - 保存到图库：用系统的保存按钮控件，不需要申请存储权限；
  - 分享；
  - 复制到剪贴板。
- **SSH**：截取终端区域，同时提供「导出为文本」。
- **证据包（Pro）**，包含：
  - 截图；
  - 当前会话摘要：协议、远端分辨率、缩放、编解码、帧率、网络路径、最近一次错误；
  - 用户选择的最近 1 到 10 分钟诊断时间线。
  预览时可以逐项删掉，然后保存成一个压缩包，或者作为反馈邮件的附件。
- **不做**：录屏，以及任何自动上传。AI 不读截图原图，只读结构化摘要。

### 2.3 阶段

| 阶段 | 内容 | 主要文件 | 完成条件 |
|---|---|---|---|
| E0 | 原生「读回下一帧」 | `gl_renderer.cpp/.h` 等，见下方说明 | 硬解、软解、RDP 三条路径都截出正向、原始尺寸的画面；不阻塞渲染线程；会话结束时未完成的请求返回取消 |
| E1 | 截屏入口和预览 | `RemoteSessionTopBar.ets`（启用 RustDesk 的占位项）、`RdpSessionToolbar.ets`、`VncSessionToolbar.ets`、`MoonlightSessionToolbar.ets`，新增 `components/SessionScreenshotSheet.ets` | 三种设备上都能保存、分享、复制；后台、锁屏、断开时安全取消 |
| E2 | 证据包组装、预览和删项 | 新增 `services/pro/evidence/*`，复用诊断抓取的事件窗口 | 大小有上限；临时文件会清理；失败会明确显示 |
| E3 | 邮件附件和分享 | `AiMailService`、反馈页 | 附件添加失败不能显示成「已发送」 |
| E4 | 评估录屏 | — | 只出评估结论，不进首发 |

E0 原生读回的做法：
- 在 `PresentFrame` 和 `PresentRawBGRA` 里接受一次读回请求。
- 硬解路径：把源纹理按远端原始分辨率画到离屏缓冲，再读回。这样不受窗口缩放和黑边影响，也复用 10-09 修好的 OES 程序。
- RDP 和软解路径：直接复制当前的 BGRA 帧。
- 新增 NAPI `captureRendererFrame(handle)`，返回宽、高和 RGBA 数据，ArkTS 侧用它生成 PixelMap。

截屏的方向要用 10-09 的倒置问题回归一遍：PC 模拟器 H.264、VP9，以及 Pad 硬解。

## 3. A 跨协议自动化方案（第三优先）

### 3.1 现状

- 工作区（`services/pro/workspace/WorkspacePolicy.ets`）的每一项包括主机、协议、顺序、是否自动连接、视图和 PC 窗口位置，打开时一键依次打开。
- SSH 常用命令和端口转发规则都已经有，但工作区没法引用它们。

### 3.2 首发范围

- 工作区里的每台 SSH 主机，可以附加「连接后步骤」：
  - 启用某条已保存的端口转发；
  - 进入某个目录；
  - 插入某条已保存的常用命令。命令默认只插入、不回车；用户在步骤里勾选「自动执行」后才会回车。
- 步骤可以设成「上一步成功才继续」。
- 运行时有面板：显示每一步的状态，可以暂停、取消、跳过、重试。
- 安全规则：
  - 只能引用已保存的命令和转发，不能临时写任意命令。
  - 第一次运行前，完整预览所有步骤。
  - 带「自动执行」的步骤，每次运行都要确认一次。
  - 主机删除、账号切换、Pro 失效或工作区被修改后，正在进行的运行会停止。
- RDP、RustDesk、VNC、Moonlight 首发只有「打开」这一个步骤，和现在一样。

### 3.3 阶段

| 阶段 | 内容 | 主要文件 | 完成条件 |

## 4. D RDP 多显示器（第四优先）

### 4.1 现状

- `multiMonitor` 和 `monitorCount` 已经从 ArkTS 传到原生，但 `freerdp_adapter.cpp`（约 8392 行）记一条日志后直接忽略，固定按单屏处理。
- 单显示器的动态分辨率（Display Control）和显示方案已经完成，包括 10-09 新增的「分辨率跟随窗口」。
- RustDesk 和 VNC 的显示器切换已经完成，可以作为界面参考。

### 4.2 分两步

- **D1 远端多屏、本地一个窗口**：
  - 向 Windows 声明 2 到 4 个显示器，接收整个跨屏桌面。
  - 本地加「显示器 1 / 2 / 全部」切换，按显示器裁剪视口，用法和 RustDesk、VNC 的显示器切换一样。
  - 好处：远端程序可以拖到第二块屏，手机、平板上切换着看。
- **D2 PC 多块物理屏**：PC 接了外接显示器时，每块本地屏开一个会话窗口，各自显示一个远端显示器。这一步依赖 PC 真机和外接屏。

### 4.3 风险

- 跨屏桌面很大（两块 4K 并排约 7680×2160），H.264 解码器和显存可能不够。D0 要先实测每台设备的上限，超出时降到每屏 1080p。
- 输入坐标要从「当前显示器」换算到「整个桌面」。
- 能不能用多显示器取决于远端服务器：Windows 家庭版不能作被控端，专业版和服务器版的行为要分别测。

## 6. 卡在外部条件的功能：怎么解锁

### 6.1 App Linking（解锁「碰一碰分享连接」和「短时访客邀请」）

现状：`ProConnectionShareConfiguration.ets` 里 `proConnectionShareBase()` 返回空字符串，所以功能关闭；`module.json5` 里还没有 https 域名。

解锁步骤：

1. 作者准备一个自己控制的 HTTPS 域名。建议买一个独立域名；也可以给现有 GitHub Pages 绑定自定义域名。
2. 在 AppGallery Connect 的 App Linking 服务里添加该域名并关联本应用，按控制台说明取得应用关联文件。
3. 把关联文件部署到该域名的 `/.well-known/` 路径下（具体文件名以控制台为准）。
4. 代码侧：
   - `module.json5` 的 skills 增加该域名的 https uris，并打开域名校验；
   - `proConnectionShareBase()` 返回该地址；
   - Pro 状态改为「试用开放」。
5. 真机验收：
   - 手机碰平板，以及反方向；
   - 接收方没装应用时跳转应用市场；
   - 过期链接、重复使用的链接被拒绝。

### 6.2 鸿蒙 PC 真机批次

等作者有了 PC 真机后，集中验收：

| 功能 | 要验什么 |
|---|---|
| 碰一碰传文件 | 手机碰 PC 的 SFTP 窗口；确认后传到当前目录；取消；大文件 |
| 同账号接续 | 手机、平板与 PC 之间的 SSH、RDP、RustDesk、VNC 接续 |
| 工作区 PC 布局 | 按保存的布局摆放窗口；窗口数量超出时的处理 |
| 手机通行密钥接入 RDP | PC 上的 RDP 会话里，Windows 网站要求安全密钥时改用手机 |
| 10-09 的 PC 改动 | 硬解画面方向（真机有没有模拟器那样的倒置）、RDP 分辨率默认整屏、各协议顶栏、SSH 工作台 |

### 6.3 USB 安全密钥

- 硬件：一把 USB-C 的 FIDO2 安全密钥。
- 远端：要支持 RDP 的 WebAuthn 重定向，一般需要 Windows 11 22H2 及以上或 Windows Server 2022，以实测为准。
- 验收：
  - 在远端浏览器里用 webauthn.io 之类的测试页注册、登录；
  - 每次使用前，本机都要确认；
  - 拔掉密钥、超时、取消。
- 通过后，正式版开放「安全密钥重定向」，状态改为「试用开放」。

### 6.4 AI 跨网连接

需要先给 RustDesk 加一条数据通道，供电脑端插件使用，再决定走 RustDesk 的中继还是自建服务。走中继涉及长期服务器成本时，按 10-02 计划第 1.2 节，不放进买断制 Pro，需要单独评估。本轮不开工。
